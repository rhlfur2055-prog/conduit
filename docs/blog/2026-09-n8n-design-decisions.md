# n8n을 직접 만들며 배운 설계 결정 6가지

n8n이나 Make 같은 노드 기반 자동화 툴을 쓰다가, "이게 안에서 어떻게 돌아가는지"가 궁금해서 직접 만들어 봤습니다. 이름은 Conduit이고, React Flow 캔버스와 Express 서버로 돼 있습니다. 노드 50여 종, 테스트 111개, 그리고 이 위에서 만든 쇼츠 영상 4편이 실제 유튜브 채널에 올라가 있습니다.

이 글은 기능 소개가 아니라, 만들면서 **"왜 이렇게 했는가"**를 정해야 했던 지점 여섯 개를 적은 것입니다. 만들기 전에는 당연해 보였는데 만들어 보니 전혀 당연하지 않았던 것들입니다.

저장소: https://github.com/rhlfur2055-prog/conduit

## 1. 노드 사이를 흐르는 건 "값"이 아니라 "아이템 배열"이다

처음 버전은 노드가 객체 하나를 받아서 객체 하나를 돌려주는 구조였습니다. 트리거 → 변환 → 출력, 깔끔했습니다. 그런데 "주문 5건을 받아서 금액이 3만 원 넘는 것만 골라 각각 처리"를 만들려니 바로 막혔습니다. IF 노드가 배열을 받으면 true/false 중 어디로 보내야 할까요? 배열 전체를 한쪽으로? 그러면 "각각"이 안 됩니다.

n8n이 왜 모든 데이터를 **아이템 배열**로 다루는지 그때 이해했습니다. 규칙을 이렇게 바꿨습니다.

- 노드 포트를 흐르는 값은 항상 `items[]`. 단일 객체를 돌려주는 옛 노드는 엔진이 `[객체]`로 감싼다.
- 일반 노드는 **아이템 하나만** 처리하도록 짠다. 반복은 엔진이 한다.
- IF/Switch/필터는 아이템 단위로 분기한다. 5건 중 3건은 true 포트로, 2건은 false 포트로.
- 집계·정렬·병합처럼 배열 전체가 필요한 노드만 `mode: 'batch'`로 표시해 통째로 받는다.

이 결정 하나로 노드 작성이 단순해졌습니다. 노드는 "아이템 하나를 어떻게 바꿀까"만 생각하면 되고, 배치 크기·병렬 실행·아이템별 오류 격리는 전부 엔진 한 곳에 있습니다.

## 2. 실행 엔진은 브라우저와 서버가 같은 코드를 쓴다

캔버스에서 "실행"을 누르면 브라우저 안에서 돌고, 서버에 저장하면 크론·웹훅으로 서버에서 돕니다. 두 실행기를 따로 만들면 언젠가 다르게 동작합니다. 그래서 엔진(`src/engine/`)을 하나로 두고 양쪽이 import 합니다.

문제는 서버에서만 되는 것들입니다. LLM 호출, Slack 전송, 에이전트 도구 실행. 이건 `globalThis.__conduitLLM` 같은 브리지로 **주입**합니다. 서버는 시작할 때 실제 구현을 꽂고, 브라우저는 주입이 없으니 노드가 "서버에서 실행하면 실제 응답이 나옵니다"라는 시뮬레이션 결과를 냅니다.

덕분에 캔버스에서 워크플로 모양을 먼저 확인하고, 그대로 서버에 올리면 같은 코드가 돕니다. 대신 브리지는 전역 변수라서 "무엇이 주입돼 있는지"가 코드에 안 보인다는 단점이 있습니다. 지금은 `server/bridges.js` 한 파일에 모아 두는 걸로 타협했습니다.

## 3. 재시도는 "몇 번"이 아니라 "어떤 오류를"이 먼저다

외부 API를 부르는 노드에 재시도를 붙일 때, 처음 떠오른 건 "3번 재시도"였습니다. 그런데 401(인증 실패)을 3번 다시 보내면 어떻게 될까요? 세 번 다 틀립니다. 인증이 틀린 요청은 시간이 지나도 맞아지지 않습니다. 재시도 횟수보다 **어떤 오류를 재시도할지**가 먼저였습니다.

지금은 오류를 두 종류로 나눕니다.

- **영구 오류** — 400, 401, 403, 404, 422, JSON 파싱 실패. 재시도하지 않는다.
- **일시 오류** — 429, 5xx, ECONNRESET 같은 네트워크 끊김. 지수 백오프로 재시도한다.

백오프에는 ±20% 지터를 넣습니다. 같은 시각에 실패한 요청 100개가 정확히 2초 뒤에 동시에 재시도하면 상대 서버를 두 번 죽이는 셈이라서요. 노드 종류별로 상한도 다릅니다. LLM은 5번까지, 이메일은 2번까지.

## 4. 실패한 아이템 하나 때문에 전체를 멈추지 않는다

주문 100건 중 1건의 데이터가 이상해서 노드가 예외를 던지면, 나머지 99건은 어떻게 될까요? 처음엔 전부 멈췄습니다. 이건 자동화 도구로서 실격입니다.

그래서 노드마다 **Continue On Fail** 옵션을 두고, 켜져 있으면 실패한 아이템만 `_error` 정보를 달아 계속 흘려보냅니다. 동시에 실패 내용은 **DLQ(실패 큐)**에 쌓여서, 나중에 화면에서 보고 그 아이템만 다시 실행할 수 있습니다.

한 가지 세부 사항은 테스트를 쓰면서 명시적으로 고정했습니다. 실패한 아이템도 출력 배열에서 **원래 자리**를 지켜야 한다는 것입니다. 실패분을 맨 뒤로 몰아 버리면 다음 노드에서 `$index`가 원래 순서와 어긋나고, 배치 크기를 바꾸면 결과 순서가 달라집니다. 이런 보장은 코드에 주석으로 적어 두는 것보다 실패하는 테스트로 남겨 두는 편이 오래갑니다.

## 5. 테스트를 붙였더니 버그가 두 개 나왔다

솔직히 처음 한 달 반은 테스트가 0개였습니다. 기능이 잘 돌아가는 것처럼 보였으니까요. 엔진에 테스트 69개를 붙이면서 실제 버그 두 개를 찾았습니다.

**중복 제거 노드가 중첩 객체를 구분하지 못했습니다.** `{u:{id:1}}`과 `{u:{id:2}}`를 같은 아이템으로 보고 하나를 지웠습니다. 원인은 `JSON.stringify(obj, Object.keys(obj).sort())`였습니다. 두 번째 인자로 키 배열을 주면 **모든 깊이**에 같은 허용 목록이 적용돼서, 바깥 키 `u`만 남고 안쪽 `id`는 사라집니다. 키를 재귀적으로 정렬한 사본을 만들어 직렬화하는 것으로 고쳤습니다.

**`"{{ a }} {{ b }}"`가 `undefined`가 됐습니다.** "문자열 전체가 표현식 하나인가"를 판별하는 정규식 `^\{\{(.+)\}\}$`가 표현식 두 개를 하나로 잡았습니다. 안쪽에 다른 `{{`가 없을 때만 단일 표현식으로 보게 했습니다.

둘 다 "잘 돌아가는 것처럼 보이던" 코드였습니다. 실패하는 테스트를 먼저 쓰고, 원인을 좁히고, 고친 뒤 회귀 테스트로 남기는 순서가 왜 필요한지 몸으로 배웠습니다.

## 6. 보안은 기능 단위가 아니라 "입구" 단위로 본다

서버에 API 키 인증을 붙이면서 가장 오래 고민한 게 코드 노드였습니다. 코드 노드는 사용자가 쓴 JavaScript를 서버에서 그대로 실행합니다. 인증 없이 외부에 열리면 누구나 서버에서 코드를 돌릴 수 있습니다.

"코드 노드를 끄는 옵션을 만들자"가 첫 생각이었습니다. 그런데 서버에서 사용자 JS가 실행되는 입구를 세어 보니 **셋**이었습니다.

1. 코드 노드
2. `{{ $json.name }}` 같은 표현식 — `new Function`으로 평가하므로 `{{ process.env.ANTHROPIC_API_KEY }}` 한 줄이면 비밀값이 나온다
3. AI 에이전트의 `run_code` 도구 — 모델이 고른 코드가 실행된다

하나만 막으면 나머지 둘로 똑같은 일을 할 수 있습니다. 그래서 스위치 하나(`CONDUIT_ALLOW_CODE`)로 셋을 같이 끄고, 기본값은 "API 키가 설정된 서버(=외부에 연 서버)에서는 꺼짐"으로 뒀습니다.

표현식은 끄면 안 되는 기능이라, 코드 실행이 꺼진 상태에서는 `new Function` 없이 `$json.a.b`, `$items[0].x`, `$items.length` 같은 **데이터 경로만** 읽는 해석기로 바뀝니다. `constructor`나 `__proto__`는 읽지 않습니다. 에이전트는 도구 목록에서 `run_code`를 빼는 것만으로는 부족해서(모델이 이름을 지어내 부를 수 있음) 실행 직전에 한 번 더 막습니다.

## 만들고 나서 달라진 것

n8n을 다시 열어 보면, 전에는 그냥 넘겼던 것들이 보입니다. 왜 모든 노드 출력이 배열인지, 왜 크리덴셜이 노드 설정과 분리돼 있는지, 왜 실행 기록에 노드별 입력·출력이 따로 남는지. 답을 직접 정해 본 사람만 보이는 것들입니다.

아직 부족한 것도 많습니다. 크론이 서버 프로세스에 묶여 있어서 재시작 사이의 실행은 그냥 사라집니다. 코드 실행이 켜진 로컬 모드에서는 여전히 `new Function`이라 샌드박스가 아닙니다. 사용자별 권한도 없고 키는 하나뿐입니다. 다음은 MCP 서버 부분을 독립 패키지로 떼어 내는 것과, LLM 노드의 출력을 통과율로 평가하는 도구입니다.

코드와 테스트는 전부 공개돼 있습니다: https://github.com/rhlfur2055-prog/conduit
