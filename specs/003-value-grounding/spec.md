# 명세: 답의 값 근거 검증 (Value Grounding)

- 기능 브랜치: `feat/agent-loop`
- 상태: 구현 완료 (2026-09-23)
- 입력 요청: NLI 모델을 가져다 쓰지 말고 "우리가 재해석해서 만들자"
- 관련: 002 벤치마크 축 B (할루시네이션) · 원칙 I "검증은 모델 밖에서"

## 문제

지금 검증기는 **인용이 원문에 글자 그대로 있는지**만 본다.
그래서 인용은 진짜인데 답이 틀린 경우를 통과시킨다.

```
인용: "결제일은 매월 14일입니다"   ← 원문에 있음 → 통과
답:   "결제일은 15일이다"           ← 틀렸는데 verified
```

오픈소스 NLI 모델은 이를 "의미 추론"으로 판정하지만, 모델 판정이라 다시 틀릴 수 있다.

## 재해석

의미 전체를 판정하지 않는다. **확인할 수 있는 값만, 코드로, 반드시** 확인한다.
할루시네이션이 가장 해로운 곳(숫자 · 날짜 · 금액 · 비율 · 영문 이름/ID)이 바로 코드로 확인 가능한 곳이다.

- 답에서 **값**을 뽑는다: 숫자(쉼표·전각 정규화, `1,200,000` = `1200000`), 영문·ID 토큰(`Office_5G`, `user_01`, `API`)
- 각 값이 **그 답이 댄 인용들 안에** 있어야 한다. 하나라도 없으면 `refuted` (`unsupported_value`)
- 논박 라운드에서 "답의 값 15 는 인용 어디에도 없다" 로 되돌린다
- `inference:true` 답(전제·반례·연결처럼 추론이 필요한 답)은 인용 밖의 값이 나올 수 있다 →
  반박하지 않고 `derived` 로 표시해 드러낸다. 요약에서 그 문장은 "추론:" 으로 시작해야 한다 (기존 규칙)

## 요구사항

- **FR-001** `extractValues(text)` — 숫자 값과 영문/ID 토큰을 정규화해서 뽑는다. 질문 번호(`Q3`)·줄 번호(`L2`, `M1`)는 뺀다.
- **FR-002** `groundValues(answer, quotes)` — 값마다 인용 안 존재 여부. 숫자는 정규화 후 **수 단위로** 비교한다 (`14` 가 `140` 안에 있다고 통과시키지 않는다).
- **FR-003** verifyQuestion 이 인용 검증 다음에 값 검증을 한다. 비추론 답의 근거 없는 값 → refuted, 추론 답 → verified + `derived` 목록.
- **FR-004** 값이 없는 답(순수 서술)은 이 검증의 영향을 받지 않는다.

## 성공 기준

- **SC-001** 정답을 아는 (인용, 답) 쌍으로 잰다 — 틀린 값을 넣은 답을 잡아내는 비율(재현율) ≥ 95%
- **SC-002** 같은 세트에서 맞는 답을 잘못 반박하는 비율(오탐) ≤ 5% — 표현만 바꾼 정답은 통과해야 한다
- **SC-003** 기존 테스트 전부 통과 (인용 검증 동작은 그대로)

## 측정 결과 (`node server/socratic.eval.js` · 값이 든 문서 줄 21개 → 맞는 답 71 · 틀린 답 82)

| | 결과 | 목표 |
|---|---|---|
| 재현율 (틀린 값을 잡음) | **97.6%** | ≥ 95% ✅ |
| 오탐률 (맞는 답을 반박) | **0.0%** | ≤ 5% ✅ |
| 한국어 단위(4,200만 원)로 쓴 맞는 답 반박 | 0% (4건) | — `만`·`억` 을 풀어 비교 |

- 놓친 2건: `2~3일` 의 2 를 3 으로 바꾼 답 — 3 이 같은 줄에 원래 있어서 코드로는 구분할 수 없다 (아래 한계).
- 새 모델·새 오픈소스 없이 코드로만 구현 (NLI 모델을 쓰지 않기로 한 결정, 2026-09-23).

## 한계 (이 기능이 막지 못하는 것)

- 값이 없는 의미 오류 — "자동이체가 켜져 있다" 를 "꺼져 있다" 로 뒤집은 답. 부정·반의어는 코드로 판정하지 않는다 (오탐이 많다).
- 단위 · 계산 오류 중 인용에 같은 숫자가 우연히 있는 경우 (`14일` 인데 인용의 다른 곳에 `14%` 가 있는 경우) — 드물다고 보고 측정으로 확인한다.
